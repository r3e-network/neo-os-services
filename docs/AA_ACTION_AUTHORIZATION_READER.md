# Trusted Rust AA action reader

The selected host network overlay and reviewed network registry choose the RPC endpoint, magic, genesis, canonical core and recovery verifier. The existing scoped RPC resolver selects one endpoint once; no request URL, owner, proof or snapshot is an authority input. One synchronous NeoRpcClient with a one-element endpoint list performs identity preflight and every subsequent read. Host egress refuses redirects; errors exposed to the ticket flow are fixed and do not include upstream responses or configuration.

The reader validates core/verifier target binding before I/O, checks actual network magic/genesis and required read/consume ABI, then gets the latest validated index with getstateheight and its canonical nonzero32-byte getstateroot. Both getVerifier(rawAccount) and getActionAuthorization(rawAccount,derivedMaster) use invokefunctionhistoric with that SAME explicit root. There is no latest invocation fallback. The header is fetched at that exact validated height; its index must match. Its age must fit the existing30s RPC timeout before/after reads, under the host clock. No latest header is used. The host clock supplies observed_time_ms and rejects expired requests before and after I/O. Revocation after the selected snapshot remains enforced by AA current-epoch/nonce consumption checks; a snapshot is not a promise about later chain state. This is a trusted RPC boundary, not SPV/validator/state-proof verification.

The authorization return must be exactly one HALT stack item containing nine typed fields: protocol4, core Hash160, verifier Hash160, nonzero current verifier owner Hash160, raw UTF-8 network, raw UTF-8 account text, positive canonical epoch, canonical nonce, allowed Boolean true. Owner is not reconstructed from a posted owner or the core backup owner. Stored opaque text is never normalized. Grant, epoch and nonce must match the verified identity/request; an old/unknown ABI, FAULT, malformed result, identity mismatch, expired time, root/header mismatch or stale root refuses issuance.

Hash byte order is explicit: registry contract targets use display order; AA269 HashToHex emits raw UInt160 bytes. Expected ticket targets and returned Hash160 values are compared in raw order. RPC account/master ByteArray arguments use canonical base64 of their exact raw bytes. No implicit 20-byte-to-text heuristic is used.

The four changed DID13 files and all17 mappings are pinned byte-exactly; Services supplies only the trusted reader composition. Legacy JS has no reader and remains unable to issue action-v4. No deployment/owner enrollment is performed. Current configured legacy57-method recovery contracts lack v4 and must refuse. Source/fake evidence is not native/runtime/deployment GO; owning Rust tests require a later allocation.
